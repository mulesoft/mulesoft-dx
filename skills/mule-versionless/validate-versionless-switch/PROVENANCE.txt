=== Partially-supported modules: the dw::Runtime fix (nested-FQN model, shipped 2026-10-23) ===
Correction (4) above, paired with FIX 1 in the plugin jar. The shipped jar (sha256 e582673466…,
91,367,840 bytes) and CLI (sha256 63fbb0bf…, 10,037 bytes) carry it. This SUPERSEDES the retired
`partiallySupported`-partition model an earlier bundle shipped (plugin 52a8b91d…, 91,368,489 bytes);
the schema and reporting rule are different — see "What changed from the retired model" below.

The bug: `import try from dw::Runtime` and `import * from dw::Runtime` were wrongly reported as a
BLOCK. dw::Runtime LOADS on the versionless engine and all of try/fail/wait/props run; only `version`
is unimplemented (version() -> native("system::version"), in no Rust dispatch table). Two layers each
over-generalised from that one gap: the manifest classified the module all-or-nothing, and the Java
axis blocked any import of an unsupported module regardless of which member was imported. Confirmed a
validator BUG (not an app defect) by Dmitrii Popov + Shobana Ranganathan; the AAA app source must NOT
be "cleaned up" — the fix is in the validator.

Schema (nested-FQN, NOT a partition key): the bare module `dw::Runtime` stays in modules.unsupported;
each runnable member is listed as its own FQN in modules.supported —
    "unsupported": [ ..., "dw::Runtime", ... ]
    "supported":   [ ..., "dw::Runtime::try", "dw::Runtime::fail", "dw::Runtime::props",
                          "dw::Runtime::wait", ... ]
`version` has NO member entry, so it inherits the module's unsupported verdict. This keeps the top-
level keys intact (Gson drop-in) and needs no new schema field. The jar reads supported/unsupported
string lists only.

Reporting rule (DwxClassifier + SymbolCollector in the plugin jar), as shipped with FIX 1:
  - Bare (`import dw::Runtime`) / wildcard (`import * from dw::Runtime`) → one MODULE ref. The module
    is in modules.unsupported, so the MODULE case fires; DwxClassifier.isPartiallySupported("dw::Runtime")
    sees at least one nested member FQN (dw::Runtime::try) in modules.supported and downgrades the
    finding from BLOCK to INFO (rule dwx.module.unsupported, severity INFO, message "only partially
    supported … verify the script does not call an unsupported member such as version"). This is FIX 1.
  - Selected (`import try from dw::Runtime`) → one MODULE_MEMBER ref per member; blocks only if the
    member's own FQN (dw::Runtime::try) is NOT in modules.supported (rule dwx.module.function.unsupported,
    BLOCK). So `import try …` is clean while `import version …` still BLOCKs. Alias (`import try as t`)
    is keyed on the original name `try`, not the alias.
  - The implicit `import * from dw::Core` every parse carries is unaffected: its FQN is dw::Core, not
    the manifest's Core key `dw`, so it never matches and never flags.

FIX 2 (writer passthrough), shipped in the SAME jar, disjoint from FIX 1: a WRITER whose format has
no byte serializer (application/java) and is listed in writers.passthrough is reported INFO (rule
dwx.writer.passthrough) rather than BLOCK. The shipped override carries NO writers.passthrough key, so
FIX 2 is INERT in this bundle (application/java is instead handled by correction (3), which lists it in
writers.supported). The code path is present and tested; it fires only if a future refreshed override
adopts the writers.passthrough tier.

FOOTGUN — the jar and the override MUST carry the same shape. FIX 1's MODULE case only fires when the
bare module is IN modules.unsupported. If a stale override reverts to the retired partition shape
(dw::Runtime REMOVED from unsupported + a `partiallySupported` key), the MODULE case matches nothing
and the wildcard import produces NO finding at all — a silent false negative, strictly worse than BLOCK
or INFO. docs/UPDATING.md §2b correction (4) enforces the nested-FQN shape and its post-conditions
assert it. Refresh the jar and override together.

What changed from the retired model: the earlier bundle shipped a `partiallySupported: [{module,
unsupportedFunctions}]` partition read by a bespoke DwxClassifier.unsupportedModuleNames fold, and
blocked bare/wildcard imports (dwx.module.unsupported, BLOCK). The shipped model drops that key
entirely, models partial support as nested member FQNs (matching mule-versionless `309a560e1` "Unwrap
dw::Runtime into nested member FQNs"), and downgrades the wildcard to INFO via FIX 1. The retired
fail-closed test (partialModuleWithoutUnsupportedFunctionsFailsClosed) no longer applies; the
nested-FQN model has no partition entry to malform.

Surgical, NOT regenerated: only dw::Runtime's nested members were added to the override by hand. The
committed golden base manifest is ~8 weeks stale; a wholesale regenerate would drag in unrelated
module-support growth and drift many perf-app findings. Idempotent re-apply: docs/UPDATING.md §2b
correction (4). Upstream, the real fix lives in mule-versionless dwx-rust (generator emits the nested
member FQNs, `309a560e1`) + the plugin's dwcompat axis (SymbolReference.MODULE_MEMBER, SymbolCollector
per-member collection, DwxClassifier per-member judging + isPartiallySupported). When a refreshed
generated manifest already carries the nested dw::Runtime members, correction (4) drops out like the
other three.
